# T09 文档管理阶段总结

## 阶段目标

在 T07 的文档解析与版本模型、T08 的向量入库基础上，补齐文档生命周期管理能力，让用户能够查看、定位、删除和重新处理知识库中的文档。

## 产出

新增：

- `backend/app/services/document_management.py`
- `backend/app/services/document_reindex.py`

修改：

- `backend/app/routers/documents.py`
- `backend/app/schemas/document.py`
- `backend/app/services/document_ingestion.py`

## 已实现接口

- `GET /api/v1/knowledge-bases/{knowledge_base_id}/documents`
- `GET /api/v1/knowledge-bases/{knowledge_base_id}/documents/{document_id}`
- `GET /api/v1/knowledge-bases/{knowledge_base_id}/documents/{document_id}/versions`
- `GET /api/v1/knowledge-bases/{knowledge_base_id}/documents/{document_id}/versions/{version_id}`
- `DELETE /api/v1/knowledge-bases/{knowledge_base_id}/documents/{document_id}`
- `POST /api/v1/knowledge-bases/{knowledge_base_id}/documents/{document_id}/reindex`

## 核心流程

1. 路由通过 JWT 获取当前用户，并校验知识库归属。
2. 文档管理服务按 `knowledge_base_id + document_id` 查询逻辑文档，返回当前版本或版本历史。
3. 指定版本查询使用 `document_versions.id`，也就是接口中的 `version_id`；`version_number` 只是文档内部的顺序号。
4. 删除时先删除 Chroma 向量，再删除原始文件，最后删除 MySQL 中的 document、version 和 chunk 记录。
5. 重新索引只允许处理最新的 `failed` 版本，清理旧 chunk/向量后重新执行解析、切分、Embedding、Chroma 入库和状态更新。

## 关键设计

- 所有文档接口都复用知识库所有权校验，防止跨用户读取或操作文档。
- 列表接口支持分页和 `pending/indexed/failed` 状态筛选。
- 删除操作保持向量库、文件系统和 MySQL 的清理顺序，降低孤儿数据风险。
- 重新索引复用 T07/T08 的处理链路，失败时保留 `failed` 状态和错误信息，便于重试和排查。

## 验证清单

- Swagger 中携带合法 Bearer Token 查询文档列表，返回分页结构。
- 使用列表返回的 `id` 调用文档详情和版本列表。
- 使用版本列表中每条记录的 `id` 作为 `version_id` 查询具体版本；不要把 `version_number` 当作 `version_id`。
- 删除文档后，列表、数据库记录、原始文件和向量均应不再存在。
- 没有失败版本时调用重新索引接口返回 `409 Conflict`；存在失败版本时返回重新索引后的状态。

## 阶段结论

T09 完成后，文档从上传、解析、版本化、向量化到查询、删除和失败重试的后端管理闭环已经具备。下一阶段进入 T10：基于 Chroma 的 RAG 检索服务。
