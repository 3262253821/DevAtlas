# 阶段 1：项目立项和问题分析

## 阶段状态

- 状态：已完成并经用户确认，已进入阶段 2（PRD 编写）
- 项目名称：DevAtlas｜研发知识协同平台
- 项目副标题：面向研发团队的版本化知识库与 AI 辅助故障分析系统
- 项目根目录：`E:\RagKnowledgeSystem`
- 本阶段没有编写业务代码

## 一句话定位

DevAtlas 面向研发和运维团队，统一管理技术文档及其版本，通过 RAG 和大模型帮助工程师检索知识、分析错误日志并制定排查步骤。

## 用户和角色

### 核心用户

- 值班/运维工程师：提交错误日志或故障描述，获得可能原因、排查步骤和参考资料。

### 次要用户

- 研发工程师：查阅 API 文档、数据库说明、部署文档和历史变更记录。
- 管理员：管理用户、项目、知识库和基础权限。

第一版不做复杂组织架构。基础目标是用户只能访问自己有权限的知识库和项目数据。

## 用户痛点

- 技术文档散落在本地文件、Wiki、聊天记录和代码仓库中；
- 文档更新后，旧版本和新版本容易混淆；
- 出现错误时，需要人工翻查多个文档和历史记录；
- 普通关键词搜索不一定能找到语义相关内容；
- AI 没有引用来源时，工程师无法判断答案是否可信。

## 核心业务主线

### 版本化知识库

登录 → 创建或进入项目知识库 → 上传 Markdown/TXT/PDF → 解析和切分 → 向量化和索引 → 保存文档版本 → 提问 → 返回答案和引用来源。

### AI 辅助故障分析

登录 → 输入故障标题和错误日志 → 检索当前项目知识 → 调用大模型 → SSE 流式返回 → 展示可能原因、排查步骤和参考资料 → 保存分析记录。

## MVP 范围

### P0：第一版主链路必须完成

- 用户注册、登录和 JWT 鉴权；
- 创建知识库或项目；
- 上传 Markdown、TXT、PDF；
- 文档解析、文本切分和向量化；
- 向量写入 Chroma；
- 基于文档的 RAG 问答；
- 展示引用文档和来源片段；
- 输入故障标题和错误日志；
- 生成可能原因和排查步骤；
- SSE 流式展示回答；
- 保存故障分析记录；
- 记录文档索引状态：`pending`、`indexed`、`failed`；
- 相同文件重复上传时具备幂等处理；
- 解析或索引失败时记录失败原因，不能留下半套数据；
- 文档、版本和向量片段之间保留明确关联。

### P1：主链路稳定后补充

- 文档列表和详情；
- 文档版本历史页面；
- 会话历史；
- 基础用户权限和数据隔离；
- 空状态、加载状态和错误状态；
- 接口测试和 RAG 效果测试。

说明：文档版本的数据关系在阶段 4 的数据库设计中提前确定，完整版本历史页面可以在 P1 实现。

## 明确不做

- GitLab、Jira、监控平台等第三方集成；
- 自动接入真实生产日志；
- 自动执行修复命令；
- 多 Agent；
- 复杂组织架构和审批流程；
- 微服务拆分；
- Kubernetes；
- 高并发优化；
- 模型微调；
- BM25、RRF、Reranker 等检索增强技术暂不作为首版前置条件。

## 后续增强方向

故障分析记录经过工程师确认和补充后，可以沉淀为新的知识库文档：

故障分析记录 → 人工确认/补充 → 知识草稿 → 审核后进入知识库。

该功能是后续迭代方向，不属于当前 MVP 必须完成的功能。

## 初步验收标准

- 未登录用户不能提交故障分析；
- 故障标题和日志不能为空；
- 系统能够检索当前知识库中的相关文档；
- 回答能够通过 SSE 流式展示；
- 回答完成后能够保存历史记录；
- 回答能够展示引用来源；
- 大模型调用失败时页面显示明确错误；
- 用户不能查询没有权限的知识库；
- 文档索引失败时能够展示失败状态和原因；
- 文档更新或删除后，旧向量不能继续被默认检索。

## 需求假设和项目风险

- 没有真实企业资料，需要准备结构合理的模拟研发资料，例如 API 文档、数据库说明、部署手册和故障复盘记录；
- RAG 效果取决于文档质量、切分方式、Embedding 和检索结果；
- 大模型可能产生幻觉，因此必须保留引用来源，并明确系统不保证自动修复生产问题；
- 文档版本更新、旧向量清理和索引失败回滚需要在技术设计阶段明确；
- 项目范围较大，必须严格遵守 MVP 优先级；
- LLM API 存在网络、额度、延迟和费用风险；
- 多用户权限和数据隔离存在数据泄露风险，需要在接口和检索条件两层校验；
- Redis、Docker 等技术只有在有明确用途时加入，不能为了凑技术栈。
