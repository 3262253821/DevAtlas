# DevAtlas 产品需求文档（PRD）

## 文档状态

- 版本：v0.1（阶段 2 已确认）
- 项目：DevAtlas｜研发知识协同平台
- 副标题：面向研发团队的版本化知识库与 AI 辅助故障分析系统
- 对应阶段：阶段 2：编写 PRD
- 前置文档：`01-项目立项和问题分析.md`
- 当前状态：已由用户确认，未进入代码开发

## 1. 产品概述

### 1.1 产品定位

DevAtlas 面向研发和运维团队，集中管理技术文档及其版本，并通过 RAG 和大模型帮助工程师检索知识、分析错误日志和制定排查步骤。

DevAtlas 的定位不是自动修复生产系统，而是提供有文档依据、可查看引用来源的 AI 辅助分析。

### 1.2 核心价值

- 减少工程师翻查分散文档的时间；
- 让文档更新和历史版本可追踪；
- 让故障分析有技术文档依据；
- 让 AI 回答能够展示来源，降低无法验证的风险；
- 将已确认的故障经验沉淀为后续可检索的知识。

## 2. 用户和权限范围

### 2.1 角色定义

#### 值班/运维工程师（核心用户）

- 创建和使用自己的知识库；
- 上传技术文档；
- 查询知识库；
- 提交故障标题和错误日志；
- 查看自己的分析记录和引用来源。

#### 研发工程师（次要用户）

- 查阅 API、数据库、部署和故障复盘文档；
- 使用知识库问答；
- 提交和查看自己有权限的故障分析记录。

#### 管理员

- 第一版保留管理员角色字段；
- 第一版不实现复杂组织架构、成员邀请和审批流；
- 基础管理员管理能力作为 P1 或后续迭代功能。

### 2.2 MVP 权限模型

- MVP 采用知识库所有者模型；
- 一个知识库属于一个用户；
- 用户只能访问自己创建或明确授权给自己的知识库；
- 当前不实现团队成员共享和复杂角色继承；
- 权限校验必须同时覆盖业务数据库查询和向量库检索条件。

## 3. 术语定义

- **知识库**：用户管理文档并进行检索问答的主要容器。MVP 不单独实现“项目”和“工作空间”两层对象。
- **文档**：用户上传的一个逻辑文件，例如 `部署手册.md`。
- **文档版本**：同一个逻辑文档的某一次内容快照。
- **文档块**：文档版本切分后用于向量检索的文本片段。
- **故障分析记录**：用户提交故障标题和日志后产生的一次分析任务及其结果。
- **引用来源**：回答所依据的文档、版本和文本片段。

说明：后续如果需要支持一个项目包含多个知识库，可以在技术设计阶段扩展“项目/工作空间”概念；当前 MVP 不提前实现。

## 4. 用户痛点

- 技术文档散落在本地文件、Wiki、聊天记录和代码仓库中；
- 文档更新后，旧版本和新版本容易混淆；
- 出现错误时，需要人工翻查多个文档和历史记录；
- 普通关键词搜索不一定能找到语义相关内容；
- AI 没有引用来源时，工程师无法判断答案是否可信。

## 5. 用户故事

### US-01：注册和登录

作为一名工程师，我希望注册并登录系统，以便管理自己的知识库和故障分析记录。

### US-02：创建知识库

作为一名工程师，我希望创建一个知识库，以便集中管理某个项目或技术领域的资料。

### US-03：上传技术文档

作为一名工程师，我希望上传 Markdown、TXT 或 PDF 文档，以便系统解析并建立检索索引。

### US-04：查看文档状态

作为一名工程师，我希望看到文档当前是等待索引、索引成功还是索引失败，以便判断它是否已经可以被问答使用。

### US-05：知识库问答

作为一名工程师，我希望针对某个知识库提问，并得到带来源的回答，以便快速找到相关技术知识。

### US-06：故障分析

作为一名值班工程师，我希望提交故障标题和错误日志，系统能够结合当前知识库返回可能原因、排查步骤和参考资料。

### US-07：流式查看结果

作为一名工程师，我希望分析结果逐步显示，而不是等待完整答案生成后才看到内容。

### US-08：查看历史记录

作为一名工程师，我希望查看过去的问答和故障分析记录，以便复盘之前处理过的问题。

### US-09：控制访问范围

作为一名用户，我希望不能看到其他用户没有授权给我的知识库和文档，避免知识泄露。

### US-10：重复上传和失败处理

作为一名工程师，我希望重复上传同一文件时不会产生大量重复数据；如果解析或索引失败，我希望看到失败原因并可以重新处理。

## 6. 功能范围和需求说明

### 6.1 用户认证（P0）

#### 功能

- 用户注册；
- 用户登录；
- 返回 JWT Bearer Token；
- 受保护接口校验当前用户；
- 未登录用户不能访问知识库、文档和故障分析接口。

#### 规则

- 用户名必须唯一；
- 密码只能保存哈希值，不能保存明文；
- 登录失败时不泄露“用户名不存在”或“密码错误”的过多细节；
- Token 失效后，受保护接口返回未认证错误；
- MVP 不做邮箱注册、短信验证码和密码找回。

### 6.2 知识库管理（P0）

#### 功能

- 创建知识库；
- 查看当前用户的知识库列表；
- 查看知识库详情；
- 删除知识库及其关联文档、文档块和分析记录。

#### 规则

- 知识库名称不能为空；
- 知识库名称在同一用户范围内不能重复；
- 用户不能通过修改请求参数访问其他用户的知识库；
- 删除操作需要明确确认，避免误删。

### 6.3 文档上传和管理（P0）

#### 功能

- 支持 `.md`、`.txt`、`.pdf`；
- 单文件目标限制为 10 MB；
- 保存原始文件和文档元数据；
- 计算文件哈希；
- 创建文档版本；
- 记录索引状态和错误原因；
- 查看文档列表和详情。

#### 重复和更新规则

- 同一知识库内相同文件内容再次上传时，视为重复提交，不创建重复版本；
- 同一逻辑文档内容发生变化时，创建新的文档版本；
- 文档版本必须关联对应的文档块和向量 ID；
- 删除或替换版本时，旧版本向量不能继续参与默认检索；
- 解析、切分或向量化失败时，文档状态为 `failed`，并保存可读的失败原因。

#### 索引状态

```text
pending → indexed
    ↓
  failed
```

只有 `indexed` 状态的文档版本可以参与默认问答检索。

### 6.4 知识库问答（P0）

#### 功能

- 用户选择一个知识库并提交问题；
- 系统检索相关文档块；
- 系统调用大模型生成答案；
- 返回回答内容和引用来源；
- 无足够相关资料时，明确提示依据不足。

#### 回答要求

- 回答优先基于检索到的知识库内容；
- 引用来源至少包含文档名称、版本信息或文本片段；
- 不允许把不存在的来源伪装成真实引用；
- 当检索结果不足时，不应强行给出确定结论；
- 大模型失败时，向用户显示明确的失败状态。

### 6.5 AI 辅助故障分析（P0）

#### 输入

- 故障标题：必填；
- 错误日志或故障描述：必填；
- 知识库：必选。

#### 输出

- 可能原因；
- 建议排查步骤；
- 需要进一步确认的信息；
- 参考文档和引用来源。

#### 规则

- 分析只提供辅助建议，不自动执行修复命令；
- 分析内容必须与当前知识库权限范围绑定；
- 分析完成后保存记录；
- 分析失败时记录失败状态和错误原因；
- 故障日志中的敏感信息不应在日志系统中重复打印。

### 6.6 SSE 流式返回（P0）

#### 功能要求

- 分析过程中逐步返回文本；
- 前端能够区分普通文本、引用、完成和错误事件；
- 用户主动中断时，连接能够关闭；
- 连接中断或大模型失败时，前端显示未完成状态；
- 最终结果只有在生成成功后标记为完成。

建议事件类型：

```text
token      文本片段
citation   引用来源
done       生成完成
error      生成失败
```

### 6.7 历史记录（P1）

- 查看当前用户的问答记录；
- 查看当前用户的故障分析记录；
- 查看分析标题、状态、创建时间和结果摘要；
- 点击进入详情；
- 删除自己的历史记录。

### 6.8 基础权限和数据隔离（P0/P1）

P0 必须做到：

- 所有受保护接口都能识别当前用户；
- 数据库查询带有当前用户或知识库权限条件；
- Chroma 检索带有知识库范围过滤；
- 越权访问返回拒绝，而不是返回空数据或其他用户数据。

P1 再补充：

- 管理员查看用户和知识库；
- 知识库成员共享；
- 角色细分和邀请成员。

### 6.9 前端状态和异常状态（P1）

需要覆盖：

- 加载中；
- 空知识库；
- 空文档列表；
- 上传中；
- 索引失败；
- 问答中；
- SSE 中断；
- LLM 调用失败；
- 无权限；
- 文档不存在。

## 7. 主要业务流程

### 7.1 知识库和文档流程

```text
注册/登录
  → 创建知识库
  → 上传文档
  → 文档状态 pending
  → 解析、切分、向量化
  → indexed 或 failed
  → 查看文档和版本
  → 进入问答
```

### 7.2 知识库问答流程

```text
选择知识库
  → 输入问题
  → 校验权限
  → 检索 indexed 文档版本
  → 组装上下文
  → 调用 LLM
  → 返回答案和引用
```

### 7.3 故障分析流程

```text
选择知识库
  → 填写故障标题和日志
  → 校验输入和权限
  → 检索相关文档
  → 调用 LLM
  → SSE 流式返回
  → 完成后保存记录
```

## 9. 验收标准

### 9.1 认证验收

- 注册成功后可以登录；
- 重复用户名注册被拒绝；
- 错误密码不能登录；
- 不携带 Token 访问受保护接口会被拒绝；
- 失效 Token 不能继续访问受保护接口。

### 9.2 文档验收

- 支持的文件可以上传；
- 不支持的扩展名被拒绝；
- 超过大小限制的文件被拒绝；
- 上传成功后有明确索引状态；
- 解析或向量化失败后有失败原因；
- 相同内容重复上传不会产生重复数据；
- 文档更新后能产生新版本；
- 删除后旧版本不会被默认检索。

### 9.3 问答验收

- 只能在有权限的知识库内提问；
- 问题能够检索到相关文档；
- 回答包含引用来源；
- 无相关依据时明确提示；
- LLM 失败时前端显示错误；
- 不会返回其他用户知识库内容。

### 9.4 故障分析验收

- 标题和日志为空时不能提交；
- 分析结果包含原因、排查步骤和参考资料；
- 结果通过 SSE 流式显示；
- 生成完成后保存分析记录；
- 中断或失败时记录状态正确；
- 不执行任何自动修复命令。

## 10. 非功能要求

### 安全

- 密码只保存哈希值；
- API Key 只通过环境变量配置；
- 上传文件限制扩展名、大小和保存路径；
- 防止路径穿越；
- 所有知识库查询执行权限过滤；
- 不在普通日志中打印 Token、密码或完整敏感日志。

### 可维护性

- 路由、业务逻辑、数据访问、RAG 核心逻辑分层；
- 文档、版本、文档块和故障记录有明确关系；
- 重要状态和错误原因可追踪；
- 关键流程有接口测试。

### 可解释性

- 回答展示引用来源；
- 故障分析明确标注“辅助建议”；
- 后续使用固定问题集评估检索质量；
- 不使用没有实际测试依据的性能和准确率数字。

## 11. 成功判断方式

第一版不预设虚假的业务指标，使用以下方式验证：

- P0 主链路能够完整跑通；
- 固定测试用户之间不存在越权读取；
- 固定测试文档的问题能够检索到相关片段；
- 回答来源与实际检索片段一致；
- SSE 正常、失败和中断场景都有验证；
- 文档重复上传、更新、删除和索引失败场景都有测试记录；
- 后续建立一组固定 RAG 问题集，记录 Recall@K 或来源命中情况。

## 12. 非目标和后续迭代

当前版本不做：第三方平台集成、生产日志自动接入、自动修复、多 Agent、复杂组织架构、微服务、Kubernetes、高并发优化和模型微调。

后续可以考虑：

- 故障分析记录转知识草稿；
- BM25 + 向量混合检索；
- Reranker；
- RAG 评测集和检索调试台；
- 知识库成员共享和角色管理；
- GitLab、Jira 或监控系统接入。

## 13. 阶段 2 评审确认项

阶段 2 已确认以下决策：

1. MVP 用户是否采用“知识库”作为主要容器，不在第一版单独实现项目/工作空间两层结构；
2. 核心用户是否为值班/运维工程师，研发工程师为次要用户；
3. 文档索引状态、重复上传幂等、引用来源和旧向量清理是否纳入第一版验收；
4. 故障分析记录转知识是否明确放到后续迭代；
5. P0/P1 划分和页面范围是否接受。

确认结果：以上五项全部接受。进入阶段 3：页面和业务流程设计。
