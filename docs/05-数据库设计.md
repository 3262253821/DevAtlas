# 阶段 5：数据库设计

## 文档状态

- 版本：v0.1（阶段 5 已确认）
- 数据库：MySQL 8.0.41
- 连接：`127.0.0.1:3306/dev_atlas`
- 存储引擎：InnoDB
- 字符集：`utf8mb4`
- 时间：UTC `DATETIME(6)`
- 当前状态：已由用户确认，未进入代码开发

## 1. 设计原则

- MySQL 保存用户、权限、文档、版本和分析记录等业务事实；
- Chroma 保存文档块的向量和检索 metadata，不替代 MySQL；
- 文档、文档版本、文档块分开建表；
- 当前用户和知识库之间通过 `owner_id` 建立权限边界；
- 业务状态使用字符串值，不使用 MySQL ENUM，方便后续扩展和迁移；
- 所有表使用 `created_at`，会变化的表增加 `updated_at`；
- 删除文档前由 Service 清理文件和 Chroma，再删除 MySQL 数据；
- 密码只保存哈希，不保存明文；
- API Key 不进入数据库。

## 2. 业务关系

```text
users
  └── knowledge_bases
        ├── documents
        │     └── document_versions
        │            └── document_chunks → Chroma
        ├── conversations（P1）
        │     └── messages（P1）
        │            └── message_citations（P1）
        └── incidents
              └── incident_citations
```

## 3. 表设计

### 3.1 users

用户表。

| 字段 | MySQL 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | BIGINT UNSIGNED | PK, AUTO_INCREMENT | 用户 ID |
| username | VARCHAR(50) | NOT NULL, UNIQUE | 登录名 |
| password_hash | VARCHAR(255) | NOT NULL | 密码哈希 |
| role | VARCHAR(20) | NOT NULL, DEFAULT `user` | `user`/`admin`，首版只保留基础角色 |
| is_active | TINYINT(1) | NOT NULL, DEFAULT 1 | 是否允许登录 |
| created_at | DATETIME(6) | NOT NULL | 创建时间 |
| updated_at | DATETIME(6) | NOT NULL | 更新时间 |

索引：`uq_users_username(username)`。

### 3.2 knowledge_bases

知识库表，MVP 的主要容器。

| 字段 | MySQL 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | BIGINT UNSIGNED | PK, AUTO_INCREMENT | 知识库 ID |
| owner_id | BIGINT UNSIGNED | NOT NULL, FK users.id | 所有者 |
| name | VARCHAR(100) | NOT NULL | 名称 |
| description | VARCHAR(500) | NULL | 描述 |
| created_at | DATETIME(6) | NOT NULL | 创建时间 |
| updated_at | DATETIME(6) | NOT NULL | 更新时间 |

约束和索引：

- `UNIQUE(owner_id, name)`：同一用户下名称不能重复；
- `INDEX(owner_id, updated_at)`：查询当前用户知识库列表。

删除策略：删除知识库时，Service 先清理其 Chroma 向量和文件，再删除关联业务数据。

### 3.3 documents

逻辑文档表。一个文件名对应一个逻辑文档，内容变化时产生新版本。

| 字段 | MySQL 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | BIGINT UNSIGNED | PK, AUTO_INCREMENT | 文档 ID |
| knowledge_base_id | BIGINT UNSIGNED | NOT NULL, FK | 所属知识库 |
| original_filename | VARCHAR(255) | NOT NULL | 用户上传的文件名 |
| normalized_filename | VARCHAR(255) | NOT NULL | 用于判断逻辑文档的规范化文件名 |
| file_type | VARCHAR(20) | NOT NULL | `md`/`txt`/`pdf` |
| current_version_id | BIGINT UNSIGNED | NULL, FK | 当前版本，创建版本后回填 |
| created_at | DATETIME(6) | NOT NULL | 创建时间 |
| updated_at | DATETIME(6) | NOT NULL | 最近更新时间 |

约束和索引：

- `UNIQUE(knowledge_base_id, normalized_filename)`：同一知识库内同名文件视为同一逻辑文档；
- `INDEX(knowledge_base_id, updated_at)`；
- `current_version_id` 在创建版本后更新，避免每次列表查询都猜测最新版本。

### 3.4 document_versions

文档版本表。每次内容变化产生一个版本。

| 字段 | MySQL 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | BIGINT UNSIGNED | PK, AUTO_INCREMENT | 版本 ID |
| document_id | BIGINT UNSIGNED | NOT NULL, FK | 所属逻辑文档 |
| version_number | INT UNSIGNED | NOT NULL | 从 1 开始递增 |
| file_sha256 | CHAR(64) | NOT NULL | 文件内容哈希 |
| storage_path | VARCHAR(500) | NOT NULL | 原始文件相对路径 |
| file_size | BIGINT UNSIGNED | NOT NULL | 文件字节数 |
| status | VARCHAR(20) | NOT NULL | `pending`/`indexed`/`failed` |
| error_message | TEXT | NULL | 失败原因 |
| chunk_count | INT UNSIGNED | NOT NULL, DEFAULT 0 | 成功生成的文档块数量 |
| created_at | DATETIME(6) | NOT NULL | 创建时间 |
| updated_at | DATETIME(6) | NOT NULL | 状态更新时间 |

约束和索引：

- `UNIQUE(document_id, version_number)`；
- `UNIQUE(document_id, file_sha256)`：相同内容不重复创建版本；
- `INDEX(document_id, status)`；
- 只有 `indexed` 版本的 chunks 允许进入默认检索。

### 3.5 document_chunks

文档版本切分后的文本片段。MySQL 保存原文和来源信息，Chroma 保存对应向量。

| 字段 | MySQL 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | BIGINT UNSIGNED | PK, AUTO_INCREMENT | 文档块 ID |
| document_version_id | BIGINT UNSIGNED | NOT NULL, FK | 所属版本 |
| chunk_index | INT UNSIGNED | NOT NULL | 版本内顺序，从 0 开始 |
| content | LONGTEXT | NOT NULL | 文本片段 |
| vector_id | VARCHAR(255) | NOT NULL, UNIQUE | Chroma 中的 ID |
| page_number | INT UNSIGNED | NULL | PDF 页码，TXT/MD 可为空 |
| char_start | INT UNSIGNED | NULL | 原文起始位置 |
| char_end | INT UNSIGNED | NULL | 原文结束位置 |
| created_at | DATETIME(6) | NOT NULL | 创建时间 |

约束和索引：

- `UNIQUE(document_version_id, chunk_index)`；
- `UNIQUE(vector_id)`；
- `INDEX(document_version_id, chunk_index)`。

### 3.6 conversations（P1）

知识库问答会话。

| 字段 | MySQL 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | BIGINT UNSIGNED | PK, AUTO_INCREMENT | 会话 ID |
| owner_id | BIGINT UNSIGNED | NOT NULL, FK | 创建者 |
| knowledge_base_id | BIGINT UNSIGNED | NOT NULL, FK | 会话所在知识库 |
| title | VARCHAR(200) | NULL | 会话标题 |
| created_at | DATETIME(6) | NOT NULL | 创建时间 |
| updated_at | DATETIME(6) | NOT NULL | 最近消息时间 |

索引：`INDEX(owner_id, updated_at)`、`INDEX(knowledge_base_id, updated_at)`。

### 3.7 messages（P1）

问答会话中的用户消息和 AI 消息。

| 字段 | MySQL 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | BIGINT UNSIGNED | PK, AUTO_INCREMENT | 消息 ID |
| conversation_id | BIGINT UNSIGNED | NOT NULL, FK | 所属会话 |
| role | VARCHAR(20) | NOT NULL | `user`/`assistant` |
| content | LONGTEXT | NOT NULL | 消息内容 |
| status | VARCHAR(20) | NOT NULL, DEFAULT `completed` | `streaming`/`completed`/`failed` |
| created_at | DATETIME(6) | NOT NULL | 创建时间 |

索引：`INDEX(conversation_id, created_at)`。

### 3.8 message_citations（P1）

问答 AI 消息引用的文档块。

| 字段 | MySQL 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | BIGINT UNSIGNED | PK, AUTO_INCREMENT | 引用 ID |
| message_id | BIGINT UNSIGNED | NOT NULL, FK | AI 消息 |
| document_chunk_id | BIGINT UNSIGNED | NOT NULL, FK | 来源文档块 |
| citation_index | INT UNSIGNED | NOT NULL | 回答中的引用序号 |

约束：`UNIQUE(message_id, citation_index)`、`INDEX(document_chunk_id)`。

### 3.9 incidents

故障分析记录。它和普通问答是不同的业务对象。

| 字段 | MySQL 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | BIGINT UNSIGNED | PK, AUTO_INCREMENT | 故障记录 ID |
| owner_id | BIGINT UNSIGNED | NOT NULL, FK | 提交者 |
| knowledge_base_id | BIGINT UNSIGNED | NOT NULL, FK | 使用的知识库 |
| title | VARCHAR(200) | NOT NULL | 故障标题 |
| input_content | LONGTEXT | NOT NULL | 日志或故障描述 |
| status | VARCHAR(20) | NOT NULL | `streaming`/`completed`/`failed`/`cancelled` |

| error_message | TEXT | NULL | 失败原因 |

### 3.10 incident_citations

| 字段 | MySQL 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | BIGINT UNSIGNED | PK, AUTO_INCREMENT | 引用 ID |
| incident_id | BIGINT UNSIGNED | NOT NULL, FK | 故障分析记录 |
| document_chunk_id | BIGINT UNSIGNED | NOT NULL, FK | 来源文档块 |
| citation_index | INT UNSIGNED | NOT NULL | 引用序号 |

约束：`UNIQUE(incident_id, citation_index)`、`INDEX(document_chunk_id)`。

## 4. 外键和删除策略

### 4.1 逻辑关系

- `users 1:N knowledge_bases`；
- `knowledge_bases 1:N documents`；
- `documents 1:N document_versions`；
- `document_versions 1:N document_chunks`；
- `knowledge_bases 1:N incidents`；
- `incidents 1:N incident_citations`；
- `knowledge_bases 1:N conversations`；
- `conversations 1:N messages`。

### 4.2 删除顺序

删除文档时：

1. 删除 Chroma 中该文档的 vector IDs；
2. 删除原始文件；
3. 在事务中删除 `document_chunks`、`document_versions`、`documents`。

删除知识库时：

1. 找到所有文档版本和 vector IDs；
2. 删除 Chroma 向量和上传文件；
3. 删除 MySQL 关联数据；
4. 删除知识库本身。

数据库外键可以使用级联删除业务行，但不能依赖数据库级联清理 Chroma 和文件系统。

## 5. Chroma metadata 设计

Chroma 使用单个集合，例如 `devatlas_knowledge_chunks`。每个向量 ID 稳定生成：

```text
kb:{knowledge_base_id}:doc:{document_id}:version:{version_id}:chunk:{chunk_index}
```

metadata 至少包含：

```json
{
  "owner_id": 1,
  "knowledge_base_id": 1,
  "document_id": 10,
  "document_version_id": 21,
  "version_number": 2,
  "chunk_index": 0,
  "source_filename": "部署手册.md",
  "page_number": null,
  "is_searchable": true
}
```

查询必须带知识库范围和可检索条件。版本替换或删除时：

- 从 Chroma 删除旧 vector IDs；
- 或在清理完成前将 `is_searchable` 置为 false，并最终删除；
- 默认检索不能依赖客户端传入的 owner_id。

## 6. 事务和一致性

### 文档入库

1. 创建或找到逻辑文档；
2. 创建 `document_versions(status=pending)`；
3. 保存文件并解析；
4. 生成 chunks 和 vectors；
5. Chroma 写入成功后写入 MySQL chunks；
6. 更新版本为 `indexed`，回填 `current_version_id`；
7. 任一步失败则记录 `failed`，清理已写入的向量和临时文件。

由于 MySQL 和 Chroma 不是同一个事务系统，Service 必须提供失败补偿逻辑，不能声称具备跨系统原子事务。

### 故障分析

1. 创建 `incidents(status=streaming)`；
2. 检索并调用 LLM；
3. 收集结果和引用；
4. 完成后更新为 `completed` 并写入 citations；
5. 失败更新为 `failed`，用户中断更新为 `cancelled`。

## 7. P0/P1 表范围

### P0

- `users`；
- `knowledge_bases`；
- `documents`；
- `document_versions`；
- `document_chunks`；
- `incidents`；
- `incident_citations`。

### P1

- `conversations`；
- `messages`；
- `message_citations`。

P1 表可以提前在设计中确定，但正式开发优先创建 P0 表，避免为了历史会话阻塞主链路。

## 8. 阶段 5 数据库评审确认项

阶段 5 已确认以下决策：

1. 文档、文档版本、文档块分表；
2. 同一知识库内用规范化文件名识别逻辑文档，内容变化创建新版本；
3. 使用 `pending/indexed/failed` 版本状态和 `file_sha256` 幂等约束；
4. MySQL 保存业务事实和原文片段，Chroma 只保存向量和 metadata；
5. 普通问答历史表属于 P1，故障分析记录属于 P0；
6. 删除时由 Service 同步清理 Chroma 和文件，不能只依赖 MySQL 外键级联；
7. 使用整数主键、InnoDB、utf8mb4 和 UTC `DATETIME(6)`。

确认结果：以上七项全部接受。进入阶段 6：拆分开发任务。
