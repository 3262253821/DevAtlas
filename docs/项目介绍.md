## 1. 项目背景

研发和运维团队的技术知识通常长期散落在个人电脑、聊天记录、过期的共享文档和代码仓库注释里。
团队缺少一个统一的、带版本语义的知识入口，由此产生三个高频问题：

1. **知识没有权威版本**：同一份接口文档存在多个副本，没有人能确定哪一份是当前生效的；
2. **检索是关键词式的**：工程师记得"大概在哪篇文档里说过"，但记不住准确术语，关键词搜索命中率低；
3. **AI 结论不可追溯**：直接让大模型回答，答案没有引用来源，工程师无法判断是否可以信任。

DevAtlas 试图用一套自洽的机制解决以上问题：用「逻辑文档 + 版本序列」管理知识的时效性，
用 RAG（检索增强生成）解决语义检索问题，用**来源引用**保证结论可追溯，
用**版本过滤**保证检索只命中当前生效版本。

项目从立项到当前阶段完成了一条可运行的 MVP 主链路：注册登录 → 创建知识库 → 上传文档并索引
→ 基于知识库问答 → 提交故障分析 → 回看历史记录。全过程在本地开发环境完成并验证。

## 2. 用户角色

| 角色 | 类型 | 真实能力边界 |
| --- | --- | --- |
| 值班／运维工程师 | 核心用户 | 提交故障标题与日志，获得流式分析结果、可能原因、排查步骤和知识库引用 |
| 研发工程师 | 次要用户 | 查阅知识库文档、检索语义相关内容、基于知识库提问并查看引用来源 |
| 管理员 | **规划中的角色** | `users.role` 字段已存在于数据模型中（默认 `user`），但用户管理、权限管理后台**本期未实现** |

**权限模型的真实状态**：当前是**单用户 owner 隔离**，不是团队协作模型。
知识库通过 `knowledge_bases.owner_id` 绑定所有者，`owner_id` 一律由服务端从 JWT 推导，
不信任客户端传入的所有者 ID。跨用户访问知识库、文档、故障记录统一返回 `404`，
避免泄露资源是否存在。

知识库共享、团队成员邀请、角色权限分配**均未实现**。

## 3. 用户痛点

| 痛点 | 具体表现 | DevAtlas 的应对方式 |
| --- | --- | --- |
| 文档版本混乱 | 更新后的文档与旧副本混在一起，无法判断哪一份当前生效 | 逻辑文档 + 版本序列，`current_version_id` 明确指向当前生效版本 |
| 知识散落 | 文档分散在本地、Wiki、聊天记录、代码仓库 | 统一上传到知识库，按知识库聚合与管理 |
| 关键词搜不到 | 记得语义但记不住术语，关键词匹配失效 | BGE 中文 Embedding + Chroma 向量相似度检索 |
| 排障靠翻资料 | 出现故障时人工翻查多份手册和历史记录 | 故障分析用「标题 + 日志」自动检索知识库并生成排查建议 |
| AI 答案不可信 | 没有引用来源，无法核实答案依据 | 回答附带 `sources`／`citation`，标明文件名、版本、切片序号和距离 |
| 重复上传产生垃圾 | 同一份文件反复上传，产生无意义的重复数据 | SHA-256 内容指纹幂等去重，重复内容不创建新版本 |
| 处理失败留下半套数据 | 解析或向量化中途失败，数据库和向量库状态不一致 | 失败保留 `failed` 状态与原因，旧版本继续可用，并做跨存储补偿清理 |

## 4. 产品定位

DevAtlas 是一个**版本化 RAG 知识协同平台**，不是通用聊天机器人，也不是完整的知识管理门户。

定位的三个支点：

1. **版本优先**：知识的第一属性是"哪个版本当前生效"。检索默认只召回 `indexed` 且是当前版本的切片，
   旧版本不会污染答案，处理失败也不会让知识库失去可用内容。
2. **引用优先**：任何 AI 生成的结论都必须携带可核对的来源片段。检索不到依据时，
   系统**明确说明知识库没有相关内容**，而不是让大模型自由发挥。
3. **边界清晰**：DevAtlas 只做"辅助分析"，不接入生产监控、不自动执行修复命令、
   不承诺自动化运维。分析结果需要工程师自己确认。

**非定位**：不是生产可用的运维平台，不是多租户 SaaS，不是模型训练平台，不是通用文档管理系统。

**技术边界**：后端是模块化单体（分层为 `routers / schemas / services / models`），
不是微服务；向量检索使用 Chroma 本地持久化，没有引入外部向量数据库服务。

## 5. 使用场景

### 场景一：新人查阅团队规范

新成员登录后进入「DevAtlas 开发演示知识库」，在问答页提问：

```text
忘记密码后应该通过什么流程处理？
```

系统从已索引的 `DevAtlas团队入门手册.txt` 中召回相关切片，流式生成回答，
并在下方列出引用来源（文件名、版本号、切片序号、距离）。

### 场景二：值班排障

值班工程师遇到线上告警，把日志粘贴进故障分析页：

```text
标题：订单服务生产环境返回 502
日志：gateway ERROR upstream prematurely closed connection
      POST /api/orders returned 502
```

系统以「标题 + 日志」为查询检索知识库，结合 `订单服务故障排查手册.md` 生成排查步骤，
结果和引用一起保存为一条 `incident` 记录，事后可在「故障历史」页回看。

### 场景三：文档更新换代

研发工程师修改了接口文档后重新上传。系统识别到文件名相同但内容不同（SHA-256 不同），
为同一个**逻辑文档**创建新版本（`version_number` 递增）。只有新版本完整索引成功后，
它才成为当前生效版本；如果处理失败，旧的 `indexed` 版本仍可被检索。

### 场景四：验证知识库边界

工程师故意提问知识库里没有依据的问题（例如"公司明年的股票价格是多少？"）。
系统返回「当前知识库中没有检索到与该问题相关的内容。」，**不调用大模型**，不编造答案。
这一行为用于验证 RAG 的知识边界。

### 场景五：故障复盘归档

故障处理结束后，在「故障历史」中查看当时的输入日志、分析结果和引用切片，
作为复盘材料使用。

> 说明：故障分析结果**不会**自动写回知识库成为新文档。把故障记录转化为知识草稿、
> 经人工审核后入库，属于后续规划方向，当前未实现。

## 6. MVP 范围

### 6.1 已纳入 MVP（当前已完成）

- 用户注册、登录、JWT 鉴权（HTTP Bearer）；
- 知识库创建、列表、详情、删除，owner 隔离；
- `.md` / `.txt` / `.pdf` 上传，扩展名、大小、文件名与路径安全校验；
- 文档解析、文本切分、BGE 向量化、Chroma 入库；
- 逻辑文档与版本序列管理，`pending / indexed / failed` 状态；
- 相同内容重复上传的 SHA-256 幂等处理；
- 解析／向量化失败时保留失败原因，旧版本继续可检索；
- 失败版本重新索引；
- 基于当前生效 `indexed` 版本的 Top-K 语义检索；
- 带来源引用的 RAG 问答（普通 JSON + SSE 流式）；
- 故障分析（SSE 流式），记录 `incidents` 与 `incident_citations`；
- 故障历史列表、详情与删除；
- 文档删除时的向量、文件和数据库三段清理；
- Vue 3 前端页面与浏览器端完整联调。

### 6.2 MVP 中保留结构但未落地的部分

- **问答历史持久化**：未实现，因此流式接口 `done` 事件中的 `conversation_id`
  （回显请求值或 `null`）与 `message_id`（恒为 `null`）目前只是接口结构占位；
- **用户管理后台**：`users.role` 字段存在，但没有管理端功能。

### 7.2 真实数据模型（7 张表）

| 表 | 关键字段与约束 |
| --- | --- |
| `users` | `id`、`username`（唯一）、`password_hash`、`role`（默认 `user`）、`is_active`、`created_at`、`updated_at` |
| `knowledge_bases` | `id`、`owner_id`（FK users, CASCADE）、`name`、`description`；唯一约束 `uq_knowledge_bases_owner_name(owner_id, name)` |
| `documents` | `id`、`knowledge_base_id`（FK, CASCADE）、`original_filename`、`normalized_filename`、`file_type`、`current_version_id`（FK document_versions, SET NULL）；唯一约束 `uq_documents_knowledge_base_filename(knowledge_base_id, normalized_filename)` |
| `document_versions` | `id`、`document_id`（FK, CASCADE）、`version_number`、`file_sha256`、`storage_path`、`file_size`、`status`、`error_message`、`chunk_count`；唯一约束 `uq_document_versions_number(document_id, version_number)` 与 `uq_document_versions_sha256(document_id, file_sha256)` |
| `document_chunks` | `id`、`document_version_id`（FK, CASCADE）、`chunk_index`、`content`(LONGTEXT)、`vector_id`(唯一)、`page_number`、`char_start`、`char_end`；唯一约束 `uq_document_chunks_version_index(document_version_id, chunk_index)` |
| `incidents` | `id`、`owner_id`（FK users, CASCADE）、`knowledge_base_id`（FK, CASCADE）、`title`、`input_content`、`status`、`result`、`error_message`、`model_name`、`created_at`、`completed_at` |
| `incident_citations` | `id`、`incident_id`（FK, CASCADE）、`document_chunk_id`（FK, CASCADE）、`citation_index`；唯一约束 `uq_incident_citations_index(incident_id, citation_index)` |

其中 `uq_document_versions_sha256` 是**重复上传幂等去重的数据层保障**，
`document_chunks.vector_id` 是 **MySQL 与 Chroma 之间唯一的关联键**。

### 7.3 存储分工

| 存储 | 真实职责 |
| --- | --- |
| MySQL | 用户、知识库、逻辑文档、版本元数据、chunk 原文、故障记录与引用 —— **业务事实来源** |
| Chroma | chunk 向量 + 检索用 metadata —— **只负责相似度检索** |

两者通过 `vector_id` 关联。检索时用 metadata 过滤 `knowledge_base_id`、
`version_id`（当前生效且 `indexed` 的版本 ID 列表）与 `is_searchable=true`。

## 9. 版本化研发知识库模块

这是 DevAtlas 的核心模块，负责"让知识有明确的当前版本"。

### 9.1 数据模型思路

```text
documents（逻辑文档）
  ├─ original_filename / normalized_filename / file_type
  ├─ current_version_id ─────────────┐  指向当前生效版本
  └─ document_versions（版本序列）    │
        ├─ version_number 递增         │
        ├─ file_sha256（内容指纹，同文档内唯一）
        ├─ status: pending | indexed | failed
        ├─ error_message / chunk_count
        └─ document_chunks（切片）
              ├─ chunk_index / content / page_number
              └─ vector_id ──────────► Chroma 中的同 ID 向量
```

**关键设计**：`documents` 是逻辑文档（用户看到的一份文件），`document_versions` 是它的版本序列。
同名文件收敛到同一条逻辑文档（`uq_documents_knowledge_base_filename`），
换内容只增加版本号，不会产生"看起来像新文件"的孤立文档。

### 9.2 上传与索引流程

```text
POST /knowledge-bases/{kb_id}/documents
→ 校验当前用户是否拥有该知识库（非本人 404）
→ 文件名规范化（NFKC 归一、去路径、清控制字符）
→ 扩展名校验（仅 .md / .txt / .pdf，否则 415）
→ 分块写入 others/uploads，随机存储名，同步计算 SHA-256（超 10 MB 返回 413）
→ 若无同内容版本：创建 pending 版本记录并提交
→ 解析（TXT/MD 按 UTF-8 读取；PDF 用 pypdf 逐页抽取文本）
→ 按句子切分（默认 chunk_size = 800，超长句子按字符硬切兜底）
→ BGE 批量向量化
→ 写入 Chroma（携带 knowledge_base_id / document_version_id / version_number /
   chunk_index / source_filename / is_searchable=true）
→ 写入 MySQL document_chunks（含 vector_id）
→ 全部成功后：status = indexed、写入 chunk_count、切换 current_version_id
```

### 9.3 幂等去重

- 识别维度是「同一逻辑文档 + 相同 SHA-256」，而不是文件名相同；
- 命中重复时，**不创建新版本**，删除本次落盘的临时文件，返回 HTTP **200** 且 `duplicate=true`
  （正常新建仍为 201）；
- 数据库层通过 `uq_document_versions_sha256(document_id, file_sha256)` 做最终保障。

### 9.4 版本切换与失败回退

这是本模块最重要的可靠性设计：

- 新版本创建后先保持 `pending`，**此时不切换** `documents.current_version_id`；
- 只有解析、切分、Embedding、Chroma 写入、MySQL chunk 保存**全部成功**，
  才把 `current_version_id` 指向新版本并标记 `indexed`；
- 任一步失败时：新版本记为 `failed`、保存截断后的 `error_message`、`chunk_count` 归零，
  **旧版本仍是 `current_version_id`，继续参与检索**；
- 如果失败发生在 Chroma 写入之后，会执行**补偿删除**（`delete_vectors(vector_ids)`），
  避免 Chroma 中残留 MySQL 无对应记录的孤立向量。

### 9.5 检索的版本过滤

检索**不是**把所有向量都拿来算相似度，而是两段式：

1. 先从 MySQL 查出该知识库中「`current_version_id` 不为空 且 状态为 `indexed`」的版本 ID 列表
   （每个逻辑文档最多只有一个版本进入该列表）；
2. 再用 `knowledge_base_id` + `document_version_id ∈ 该列表` + `is_searchable=true`
   作为 Chroma metadata 过滤条件做 Top-K 查询。

这样从机制上保证：待处理版本、失败版本、历史版本都不会污染答案。

### 9.6 重新索引与删除

- **重新索引**：针对该文档最新的 `failed` 版本。先清理该版本可能残留的旧向量与 chunk 记录，
  再重置为 `pending` 重新走完整流程；重建期间保留原 `current_version_id`，
  只有成功后才切换。没有 `failed` 版本时返回 **409**（正常业务结果，不是错误）。
- **删除文档**：顺序为「先清理 Chroma 向量 → 再删除原始文件 → 最后删除 MySQL 记录」。
  这个顺序是刻意的：如果先删 MySQL，就会丢失清理向量所需的 `vector_id`。
  MySQL 侧通过外键 CASCADE 连带删除版本、chunk 和引用记录。

## 10. 基于知识库的故障分析模块

故障分析解决"排障时人工翻资料"的问题，并把每次分析沉淀为可回看的记录。

### 10.1 与普通问答的区别

| 维度 | 知识库问答 | 故障分析 |
| --- | --- | --- |
| 输入 | 一个问题（`question`） | 故障标题（`title`）+ 日志或现象（`content`） |
| 检索查询 | 问题本身 | `title + "\n" + content` |
| Top-K | 由请求的 `top_k` 决定（1–10） | **固定 5** |
| Prompt | RAG 问答模板 | 故障分析专用模板 |
| 是否落库 | **不落库**（问答历史未持久化） | 落库为 `incidents` + `incident_citations` |
| 输出 | 回答 + 引用 | 可能原因、排查步骤 + 引用，并记录状态 |

### 10.2 处理流程

```text
POST /api/v1/knowledge-bases/{kb_id}/incidents/stream
→ 校验知识库归属（非本人 404）
→ 创建 status = streaming 的 incident 记录
→ 以 "标题\n日志" 为查询做检索（top_k = 5）
→ 若有来源：故障专用 Prompt → DeepSeek 流式生成
   → SSE 逐段返回 token
   → 保存 result 与 incident_citations，标记 completed
   → 逐个返回 citation
   → 返回 done：{"incident_id": <id>, "status": "completed"}
→ 若无来源：直接返回一条中文提示 token + done，并标记 completed（不调用大模型）
```

### 10.3 状态流转与异常处理

| 情形 | 状态变化 | 返回方式 |
| --- | --- | --- |
| 正常完成 | `streaming → completed` | SSE `token` → `citation` → `done` |
| 知识库无相关内容 | `streaming → completed` | 一条中文提示 `token` + `done` |
| 检索失败 | `streaming → failed` | **抛出 HTTP 503**（注意：不是 SSE `error` 事件） |
| 大模型失败 | `streaming → failed` | SSE `error`：`{"code":"LLM_SERVICE_ERROR","message":"大模型服务暂时不可用"}` |
| 客户端断开 | `streaming → cancelled` | 连接终止，不再发送事件 |

> 排查提示：检索失败走 HTTP 503，LLM 失败走 SSE `error` 事件。两者表现不同，
> 排查时要先确认"是请求就失败了，还是流已经开始才失败"。

### 10.4 历史与引用

- `GET /api/v1/incidents` 分页查询当前用户的故障记录，支持按 `status` 过滤；
- `GET /api/v1/incidents/{incident_id}` 返回输入内容、完整结果、错误信息和引用列表；
- `DELETE /api/v1/incidents/{incident_id}` 删除记录（204）；
- 所有查询与删除都按 `owner_id` 过滤，跨用户访问返回 404；
- 引用通过 `incident_citations.document_chunk_id` 关联到具体切片，可回溯到原文档和版本。

## 11. 项目亮点

以下亮点均对应真实实现，不含推测性描述。

### 11.1 文档版本可靠性保障与失败回退

新版本"先建设、后生效"：`pending` 阶段不切换 `current_version_id`，
全部处理成功才切换为 `indexed`。失败时旧版本不受影响，仍可被检索。
这避免了"文档更新把知识库搞挂了"的常见问题。

### 11.2 SHA-256 幂等去重

以文件内容指纹而非文件名判断重复。同一逻辑文档下 `file_sha256` 唯一，
重复上传直接复用已有版本、清理临时文件、返回 `200 + duplicate=true`，
既避免脏数据，也让重复上传成为**幂等操作**。

### 11.3 跨存储一致性补偿

MySQL 和 Chroma 不是同一个事务系统。实现上采用「先写 Chroma，再写 MySQL，
全部成功后切换版本」的编排顺序，并在失败路径上执行 `delete_vectors()` 补偿清理；
删除文档时按「向量 → 文件 → 数据库」的顺序执行，保证清理所需信息不会提前丢失。

### 11.4 双存储以 `vector_id` 关联

MySQL 保存业务事实（谁、哪个知识库、哪个文档、哪个版本、哪个切片），
Chroma 只保存向量与检索 metadata。`vector_id` 格式为
`kb:{kb_id}:doc:{doc_id}:version:{version_id}:chunk:{chunk_index}`，
**可重复计算、稳定可预测**，因此重试与补偿都不需要额外的映射表。

### 11.5 JWT owner 隔离

`owner_id` 由服务端从 JWT 推导，不信任客户端传入；知识库、文档、版本、
故障记录的每次查询和删除都叠加 owner 条件；跨用户访问统一返回 `404` 而非 `403`，
不泄露资源是否存在。密码使用 Argon2id 哈希，登录失败只返回统一凭据错误。

### 11.6 SSE 流式输出

问答与故障分析都基于 `text/event-stream`。后端用统一的 `_sse_event()` 生成
`event:` / `data:` 文本（`ensure_ascii=False`，中文不转义），并设置
`Cache-Control: no-cache`、`Connection: keep-alive`、`X-Accel-Buffering: no`；
前端用 `fetch` + `ReadableStream` 手动解析事件块，而不是 `EventSource`
（因为需要携带 `Authorization` 头且使用 POST）。

### 11.7 LangChain 作为适配层，而非安全边界

- **用了**：`langchain_core.retrievers.BaseRetriever` 做检索适配、
  `langchain_core.documents.Document` 做标准载体、`ChatPromptTemplate` 组织 Prompt；
- **没用**：LangChain 的 Agent、Chain 编排、Memory，也没有使用它的向量库封装；
- `DevAtlasRetriever._get_relevant_documents()` 内部仍然调用项目自己的
  `retrieve_context()`，`retrieve_context_with_langchain()` 只是把标准的
  `Document.metadata` 再还原成项目自己的 `RetrievedChunk`；
- 因此**权限校验、版本过滤、Chroma 查询条件、DeepSeek 客户端、SSE 事件契约
  全部仍由 DevAtlas 自己控制**。

这是一种刻意的取舍：版本过滤与 owner 隔离是业务正确性的前提，
不适合交给框架的默认行为。

### 11.8 有依据才回答

检索不到来源时，普通问答直接返回「当前知识库中没有检索到与该问题相关的内容。」，
**不调用大模型**；故障分析同样返回提示并标记 `completed`。
配合 `sources` / `citation` 中的文件名、版本号、切片序号和距离，
让工程师能自行核对结论依据。

### 11.9 前端安全渲染

模型输出统一经 markdown-it 渲染，**关闭原始 HTML 解析**，
避免模型返回的内容被当作可执行 HTML。

## 12. 技术难点

### 12.1 跨 MySQL / Chroma 的一致性补偿

难点在于两个存储没有共享事务：Chroma 写入成功、MySQL 提交失败时，
会留下"有向量但没有 chunk 记录"的孤立数据；反过来先写 MySQL 也会留下无向量的 chunk。

处理方式：
- 通过**稳定可重算的 `vector_id`** 让清理成为可能（失败的 `vector_ids` 在写入前就已确定）；
- 失败路径统一 `db.rollback()` 后调用 `delete_vectors(vector_ids)` 做补偿，并把版本记为 `failed`；
- 补偿删除本身失败时**不掩盖主失败原因**，只记录日志，主状态仍以 `failed` 为准；
- 删除文档时固定「向量 → 文件 → 数据库」的顺序。

### 12.2 版本切换时机

难点是"什么时候让新版本生效"。过早切换会让处理失败的版本进入检索，
过晚切换或忘记切换会让新内容永远不可检索；重建索引时若直接清空 `current_version_id`，
失败后会连旧内容一起丢失。

处理方式：`current_version_id` 的赋值被放在**整个处理链路的最后一步**，
与 `status = indexed` 在同一次提交中完成；重新索引期间保留原 `current_version_id`。
这一行为由测试（`test_document_ingestion_version_switch.py`）覆盖，
验证解析失败、Embedding 失败、Chroma 写入失败三种情况下旧版本仍然生效。

### 12.3 SSE 事件契约

SSE 是"HTTP 200 已经开始返回"之后才可能出错的长连接，错误处理不能只依赖状态码。

处理方式：
- 定义明确的事件契约：`token` / `citation` / `done` / `error`，顺序为
  `token…` → `citation…` → `done`；
- **请求阶段**的问题（知识库不存在 404、空问题 422、检索失败 503）用 HTTP 状态码表达；
- **流开始之后**的问题用 `error` 事件表达，字段固定为
  `{"code":"LLM_SERVICE_ERROR","message":"大模型服务暂时不可用"}`；
- `GeneratorExit` 用于识别客户端主动断开，避免连接中断被误记为服务端错误；
- 前端不能用 `EventSource`（无法自定义 `Authorization` 头、且这里需要 POST），
  因此改为 `fetch` + `ReadableStream`，需要自己处理**跨 chunk 的事件边界**：
  按空行切分事件块，未闭合的最后一段留在缓冲区，流结束时再兜底解析一次。

### 12.4 PDF / TXT / Markdown 解析与切分

难点来自三类文件的差异：TXT 与 Markdown 是纯 UTF-8 文本，
PDF 需要用 `pypdf` 逐页抽取，且**文本型 PDF 与扫描版 PDF 表现完全不同**。

处理方式：
- 解析器统一返回 `ParsedDocument(text, file_type, page_count)`，把差异收敛在一个函数里；
- TXT/MD 解码失败（非 UTF-8）报明确解析错误；
- PDF 逐页 `extract_text()` 后用空行拼接；解析后文本为空则报 `EmptyDocumentError`
  （**扫描版 PDF 因此会失败，这是已知限制，没有 OCR**）；
- 切分采用"按中文句末标点与换行先切句，再贪心拼接到不超过 `chunk_size`（默认 800）"
  的策略，单个超长句子按字符硬切兜底；
- 已确认的限制：`document_chunks` 虽然有 `page_number` 字段，但当前切分与 metadata
  构建**没有把页码映射到每个 chunk**，因此检索结果中的 `page_number` 目前为 `None`，
  只能知道 PDF 总页数，不能告诉用户具体来自第几页。**页码级定位属于后续规划。**

### 12.5 检索必须在数据库侧先做版本裁剪

如果直接把 `knowledge_base_id` 交给 Chroma 过滤，历史版本和失败版本也会被召回。
由于 Chroma 只能按 metadata 做等值/集合过滤，无法直接表达"该版本是当前生效版本"，
所以必须先查 MySQL 得到 `indexed` 且为 `current_version_id` 的版本 ID 列表，
再以 `$in` 传入 Chroma 过滤条件。这一步的代价是一次额外的 MySQL 查询，
换来的是"旧版本不会污染答案"的确定性。

## 14. 后续规划

### 14.1 短期（优先验证真实性）

1. **页码级引用定位**：在切分阶段把 chunk 与 PDF 页码绑定，填充 `page_number`，
   让引用能精确到页；
2. **问答历史持久化**：落地 `conversation_id` / `message_id` 语义，支持多轮上下文；
3. **前端代码分割**：按路由懒加载，降低首屏体积，消除构建 chunk 体积告警；
4. **异步索引任务**：把解析与向量化从请求内同步处理改为后台任务，
   配合任务状态查询，避免大文件上传时请求长时间阻塞。

### 14.2 中期（检索与协作能力）

5. **Reranker 重排序**：在向量召回后加一层精排，并建立可复现的离线评测集
   （在引入前不会宣称任何准确率／召回率提升数字）；
6. **混合检索**：评估 BM25／关键词召回与向量召回融合（RRF）的收益；
7. **知识库共享**：支持知识库成员与只读／可写角色，在保持 owner 隔离正确性的前提下扩展权限模型；
8. **故障记录沉淀为知识**：故障分析记录经人工确认与补充后生成知识草稿，
   审核通过再进入知识库文档（这一方向在立项阶段就已提出，当前**未实现**）。

### 14.3 长期（工程化，需真实需求驱动）

9. **缓存与队列**：在真实性能数据支持的前提下评估 Redis 等引入必要性；
10. **可观测性与审计**：结构化日志、请求链路追踪、操作审计；
11. **一致性问题自动对账**：定期比对 MySQL chunk 与 Chroma 向量，
    发现孤立数据后自动或半自动修复；
12. **部署与安全加固**：HTTPS、密钥托管、上传文件病毒扫描、接口限流、
    刷新 Token 与登出机制。

> 设计「逻辑文档 + 多版本」模型，通过 SHA-256 幂等去重与 `current_version_id` 延迟切换，
> 保证解析／向量化失败时旧版本仍可检索，并通过补偿删除处理 MySQL 与 Chroma 的跨存储
> 一致性问题。基于 BGE 中文 Embedding 与 DeepSeek 实现带来源引用的 RAG 问答与故障分析，
> 使用 SSE 流式返回 token 与 citation；接入 LangChain Retriever 与 ChatPromptTemplate
> 作为适配层，同时保留自有的权限隔离与版本过滤逻辑。使用 JWT 与 Argon2id 实现认证
> 与 owner 级数据隔离，并以 pytest 覆盖版本切换、失败回退和文件安全边界等场景。

**不建议**在简历中写：生产环境上线、用户量、准确率／召回率数字、Docker／K8s 部署、
Redis 缓存、多 Agent、Reranker——这些目前都**没有实现**，面试深挖时会直接失分。
