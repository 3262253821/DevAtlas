## 产品定位

DevAtlas 面向研发和运维团队，集中管理技术文档及其版本，通过 RAG 和大模型帮助工程师检索知识、分析错误日志并制定排查步骤。

核心用户是值班/运维工程师，研发工程师是次要用户，管理员只保留基础角色和权限方向。

第一版不是自动修复生产系统，而是提供有文档依据、可查看引用来源的 AI 辅助分析。

## MVP 主链路

```text
用户注册/登录
  → 创建知识库
  → 上传 Markdown/TXT/PDF
  → 解析和切分
  → BGE 向量化
  → 写入 Chroma
  → 用户提问或提交故障日志
  → 权限过滤后的 Top-K 检索
  → DeepSeek 生成
  → SSE 流式返回
  → 展示 citation
  → 保存故障分析记录
```

## MVP 必须保留的设计

- 知识库是首版主要容器，不单独实现项目/工作空间两层结构；
- 用户只能访问自己有权限的知识库；
- 权限同时过滤 MySQL 查询和 Chroma 检索；
- 文档、文档版本、文档块分表；
- 文档版本状态：`pending`、`indexed`、`failed`；
- 相同文件内容通过 SHA-256 幂等，不创建重复版本；
- 内容变化创建新版本，不覆盖历史版本；
- 只有 `indexed` 版本参与默认检索；
- 文档、版本、文档块和 Chroma vector_id 保持关联；
- 删除文档时同步清理 MySQL、原始文件和 Chroma；
- 普通问答和故障分析复用检索基础能力，但保存不同业务记录；
- 故障分析记录是 P0，普通问答历史是 P1；
- 故障分析不会自动执行修复命令。

## 用户的工作方式（必须遵守）

- 用户自己创建/修改文件、执行命令和测试；未经明确要求，AI 不自动编辑项目代码、不代替用户运行项目命令；
- 每次先检查实际工作目录和现有代码；
- 使用用户当前项目代码，不拿常规示例替代；
- 每个任务按：给一小步 → 用户操作 → 用户发送结果 → 解释实际结果 → 总体流程 → 核心代码逐行分析 → 正常/异常测试；
- 不一次生成用户无法理解的大段代码；
- 用户接受 AI 辅助编码，不要求手写每一行，但必须理解数据流、模块职责、设计原因、异常路径，并能修改和验收；
- 每完成一个可验证功能再 Git commit，不要求每个文件单独提交；
- 密码、JWT、API Key、`.env` 内容不读取、不打印、不提交。

## 真实问题处理原则

设计文档不能保证实现阶段没有错误。遇到问题先判断属于：

1. 代码实现错误；
2. API 请求/响应不一致；
3. 数据库迁移或约束错误；
4. MySQL、Chroma、LLM 等外部依赖错误；
5. 原设计遗漏或需求变化。

前四类优先修代码并补测试，第五类才更新 PRD、技术方案、API 或数据库设计。
