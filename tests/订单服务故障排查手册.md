# 订单服务故障排查手册

> 文档用途：用于 DevAtlas 知识库问答和故障分析测试。内容包含可操作的排查顺序、阈值和结果判断。

## 1. 订单服务返回 502

### 现象

客户端访问 `POST /api/orders` 时收到 `502 Bad Gateway`，网关日志中出现 `upstream prematurely closed connection`。该错误通常表示反向代理没有从上游订单服务获得有效响应，不应直接判断为数据库故障。

### 推荐排查顺序

1. 检查订单服务实例是否存活：确认健康检查 `GET /health` 返回 HTTP 200，并查看实例是否频繁重启。
2. 检查网关到订单服务的 DNS 和端口：容器网络中服务名必须解析到正确的内部地址，订单服务监听端口为 `8080`。
3. 检查订单服务最近 5 分钟的错误日志：重点搜索连接池耗尽、请求超时、未捕获异常和 OOM。
4. 检查数据库连接池：正常配置为最小连接 5、最大连接 30。活跃连接长期达到 30 时，需要排查慢 SQL 和连接未释放。
5. 检查网关超时配置：订单服务的 P95 响应时间应低于 800ms，网关 upstream 超时建议为 3s。超时配置不能代替性能问题修复。
6. 检查最近发布：如果错误从发布后立即出现，先回滚到上一版本并保留现场日志。

### 常见根因与处理

| 根因 | 证据 | 处理 |
| --- | --- | --- |
| 实例未启动 | 健康检查失败，容器无监听端口 | 恢复实例并检查启动日志 |
| 端口配置错误 | 网关连接被拒绝 | 统一服务发现和容器端口配置 |
| 连接池耗尽 | 日志出现 pool timeout，活跃连接达到 30 | 修复连接释放和慢 SQL |
| 上游处理超时 | 请求耗时超过 3s | 定位慢查询或外部依赖，不盲目增大超时 |
| 内存不足 | 容器被 OOMKilled | 降低批量大小并分析内存增长 |

## 2. 文档索引失败

文档上传成功不代表已经可以问答。只有版本状态为 `indexed` 才会写入可检索的向量。`pending` 表示仍在处理，`failed` 表示解析、Embedding 或 Chroma 入库环节出现异常。

排查顺序如下：

1. 确认扩展名属于 `.txt`、`.md` 或 `.pdf` 白名单。
2. 确认文件不是空文件，文件大小没有超过配置上限。
3. 查看版本的 `error_message`，区分解析失败、Embedding 失败和向量库失败。
4. 如果模型加载失败，检查本地 `BAAI/bge-small-zh-v1.5` 模型目录和 Python 环境。
5. 如果 Chroma 写入失败，检查 collection 是否存在、向量维度是否一致以及磁盘空间。
6. 修复原因后点击重新索引，不要创建无意义的新版本。

## 3. RAG 回答质量检查

一次问答的检索参数 `top_k=3` 表示最多召回三个相似文档切片，不代表回答长度限制为三段。回答质量检查要看三点：

- 引用文件是否属于当前知识库；
- 引用切片是否真的包含回答依据；
- distance 是否明显小于无关文档的距离。

如果知识库中没有答案，系统应该明确说明“当前知识库没有找到足够依据”，不能编造具体配置。可以把问题改写得更具体，例如将“订单有问题”改为“订单服务返回 502 时，网关 upstream 超时应该检查哪些指标”。

## 4. 权限和安全检查

- 每个查询必须同时携带当前用户身份和 `knowledge_base_id`。
- 用户 A 不能通过修改 URL 中的数字 ID 读取用户 B 的文档。
- 删除文档后，旧版本的向量不能继续出现在检索引用中。
- 文件名需要规范化，禁止 `../`、绝对路径和目录穿越。
- API Key、JWT 和数据库密码只能来自环境变量，不得进入 Git。

## 5. 故障分析记录

提交故障标题和日志后，系统会执行“向量检索 → 组装上下文 → 调用大模型 → SSE 流式返回”的流程。分析完成后应在故障历史中看到一条记录，状态为 `completed`，并可以查看输入内容、分析结果和引用关系。

如果请求被用户中止，记录可以是 `cancelled`；如果模型调用或保存失败，记录应为 `failed`，同时保留错误原因，便于后续重试和审计。
